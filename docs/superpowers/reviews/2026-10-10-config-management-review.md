## 2. Summary of what is good

- **Layering holds.** Domain config/secrets import only std/serde/chrono/uuid/thiserror; SQL only in repositories via compile-checked macros; services own transactions and write audit and outbox rows in the same transaction as the state change.
- **Crypto core is correct.** AES-256-GCM, fresh nonce per encryption, decrypt validates nonce length, AAD binds `provider:name:key_version` with tamper/mismatch tests, fail-closed protector when no key is configured.
- **Authorization is right.** `AdminUser` = `AuthUser` → `VerifiedUser` → role read from the DB on every request (demotion is immediate); MCP tokens report `MIN_UTC` verification so they can never satisfy step-up; mutating admin routes are in `SENSITIVE`; `Origin` check applies.
- **Responses are metadata-only.** No ciphertext, nonce or plaintext in DTOs; `SecretValue` redacts `Debug`/`Display`; a zero-leakage test covers list and audit JSON.
- **Migration** is forward-only, LF-pinned, constrained, and keeps the global tables out of `OWNED_TABLES`.
- **Frontend** secret input is `type="password"`, `autoComplete="new-password"`, scrubbed on open/close/submit; no localStorage; all calls via `fetchApi`.

## 5. Low / nits

- `parse_versioned_keys`: a version set like `0:<key>` leaves `primary_version = 1` with no key, so `primary_key()` panics on first encrypt; duplicate versions silently overwrite; weak/all-zero keys accepted. Validate at construction. `MasterKeyProvider` derives `Debug` over raw key bytes.
- Nonce comes from the first 12 bytes of a UUIDv4 (~92 random bits, not 96, comment is wrong). Use `Aes256Gcm::generate_nonce(&mut OsRng)`.
- `test_llm_credential(endpoint, …)` takes an arbitrary URL on a redirect-following client and detects Anthropic with `contains("anthropic")`; `x-api-key` is not stripped on cross-origin redirects. All callers pass constants today (latent SSRF). Disable redirects and gate the host. The test endpoint has no rate limit.
- Two `#[allow(clippy::too_many_arguments)]` in `provider_secrets.rs:87,117` lack the justification AGENTS §9 requires.
- Fallbacks falsify data: `list_audit_logs` maps unknown action/outcome to `SettingUpdated`/`Success`; `list_metadata` maps unknown provider/status to `Generic`/`Active`.
- Dead code: `execute_web_search`/`execute_tavily_search` (duplicated by `execute_web_search_with_services`), `is_admin_in_allowlist`, `ConfigAuditTarget::System`, `SecretStatus::Disabled/Revoked` (status unsettable), most `inference_*`/`channels_*` snapshot accessors. `hex` duplicates `base64`; `arc-swap` could be an `RwLock<Arc<_>>`.
- Account merge drops the absorbed account's role; if it was the only admin, none remains. Document or carry over.
- `SENSITIVE` lacks the admin GET routes (enforced, but unguarded against regression); no test that an MCP token gets 403 on admin routes. Email `from` validator accepts CRLF.
- Frontend: `any` in `types.ts`/`useAdmin.ts`, silent number coercion (`parseInt("1.5")`), eager (non-lazy) admin module in a 513 kB main chunk, missing tab roles/`aria-selected`, no audit pagination UI. e2e: non-admin path only checks the nav link, fake API diverges from the contract (array audit, `sec_N` ids, 201 vs 200, no step-up enforcement), redaction test would pass even if the value stayed in state, ambiguous `getByText` selectors, no Replace-flow coverage.
- Long functions: `test_credential` ~110 lines, `store_secret` ~75, `replace_secret` ~70.

## 6. Recommended order of work

1. B1, B2 (secret leaks): small, local, add regression tests asserting no secret fragment appears in errors, logs or stored audit detail.
2. B4, B3 (LLM resolution): rework `resolved_config.rs` so provider, base URL and key resolve together; tests for env-only, DB-override, user-override and mismatched-provider cases.
3. B5 (listener) and M2/M4 (boot load, serialised reload).
4. B6, B7 (frontend): fix the audit shape against the generated types, add error/step-up states, correct the fake API, add a real-contract-shaped e2e.
5. B8 and M11: decide on the admin bootstrap, then make code, `.env.example` and docs agree.
6. M-series by risk: M5–M8 (secret lifecycle), M14–M15 (validation, audit), then tests (M9) and the rest.

After the fixes, re-run: fmt, check, clippy, full test suite against `pg18-test`, `generate-openapi` diff, sqlx check, `npm run build`, and Playwright; then update `docs/superpowers/HANDOFF.md`.

## 7. Open questions for the owner

- Admin bootstrap: first-passkey promotion, `ADMIN_USERS` allowlist, or SQL-only (document it)? This changes the security model, so it is the owner's call.
  - **Decision in the code:** CLI/SQL only (`matrix-bot admin grant|revoke <account_id>`); registration and passkey enrolment never grant `admin`.
- Should admin read endpoints require fresh step-up, or only writes? The branch gates both; the docs say only writes.
  - **Decision in the code:** only writes need fresh step-up (`AdminUser`); reads need an admin session (`AdminSession`) without it, so a lapsed step-up no longer hides the console data (B7).
- Should unwired settings (M1) be removed from the registry for now, or kept as declared-but-inert with a UI badge?
  - **Decision in the code:** removed; the registry holds only settings with a live consumer.
