Why the system is shaped the way it is. `AGENTS.md` states the rules an agent must follow; this document records the design behind them, one section per area, each covered once. Topic documents:

| Topic | Document |
|---|---|

## One capability, many interfaces

The backend is a modular monolith and the source of truth for application state. Every business capability (a todo, an expense, a portfolio trade, a room lookup) is implemented once, in `application/` over `domain/`, and reached through any number of interfaces:

```text
                     ┌── Chat channels (ChannelAdapter: Matrix today; BotModule commands)
                     ├── REST API + SSE (Axum, OpenAPI)
 User / LLM ────────►├── MCP (stdio + HTTP/SSE)
                     ├── AI tool calls (llm/tools)
                     └── Web UI (React SPA, via the REST API)
                                  │
                                  ▼
                 application/<f>  (<F>Service: use cases, transactions, events)
                                  │
                                  ▼
                 domain/<f>       (entities, invariants, pure functions)
                                  │
                                  ▼
                 infrastructure/postgres  (repositories, read models)
                                  │
                                  ▼
                             PostgreSQL
```

Interfaces parse, authenticate, resolve the caller's scope, call a service, and format the reply. They never re-derive a rule. If two interfaces disagree about a capability, one of them holds business logic that belongs in the service.

### Layers and dependency direction

| Layer | Path (under `backend/src/`) | Owns | May import |
|---|---|---|---|
| Domain | `domain/<f>/` | entities, value objects, invariants, domain errors; synchronous and I/O-free | `std`, `chrono`, `uuid`, `serde`, `thiserror` only |
| Application | `application/<f>/` | `<F>Service` use cases, transaction boundaries, event publication inside the transaction (via the outbox) | `domain`, `infrastructure` |
| Interface | `interface/{http,chat,channels,mcp,events,jobs}/` | protocol translation: Axum handlers and DTOs, `BotModule` handlers, the channel adapters, registry and shared inbound pipeline (`interface/channels/`), MCP, delivery sinks (`interface/events/`) | `application`, `domain` |
| Events runtime | `events/` | SSE hub, the `LISTEN outbox` loop, the delivery dispatcher, retention; no SQL, no transport crates | `application`, `domain` |
| LLM | `llm/` | prompts, the tool-calling loop, conversation context ([`llm.md`](llm.md)) | `application`, `domain` |
| Infrastructure | `infrastructure/{postgres,inference,web}/` | repositories, HTTP clients for inference, LLM and web feeds | `domain`; never `application` or `interface` |

`backend/tests/architecture.rs` enforces the rules mechanically: layer imports, pure domain modules, zero SQL in `interface/` and `application/`, `AssertSqlSafe` confined to `infrastructure/postgres/merge.rs`, no `dotenvy::dotenv`.

`AppServices` (`application/mod.rs`) is built once per process by a composition root (`app.rs` for the server, `main.rs` for the stdio MCP server) and reaches every adapter as a parameter: `ApiState.services`, the `services` argument of `BotModule::handle_command`, and the AI turn. No adapter constructs a service itself.

The per-feature template and the settled rulings live in [`superpowers/HANDOFF.md`](superpowers/HANDOFF.md) §8–9; the realised layout design is `superpowers/specs/2026-09-24-postgres-foundation-design.md` §3.

## Single process: the front doors and the runtimes

`backend/src/app.rs` is the composition root. `main.rs` only loads `./.env`, sets up tracing, handles the `mcp` stdio mode, installs the signal handler, and calls `app::run(config, token)`. `app::run` builds one shared `Database`, one `BotHandles`, the SSE hub, the job runtime and the events runtime, then starts:

1. The Axum API server (`interface::http::start_api_server`), on a listener `app::run` binds first (`interface::http::bind`) so a bind failure stops boot rather than leaving a bot with no API and no health probes. It returns the server's `JoinHandle`.
2. The Matrix sync loop (`interface/channels/matrix/sync_loop.rs::run_bot_loop`), a reconnect loop with 5 s → 300 s backoff, run by `MatrixAdapter` (a `ChannelAdapter` the channel registry spawns) with the same `BotHandles`. `BotHandles` is built once and cloned into every reconnect generation, so `SyncHealth` survives a reconnect.
3. The job runtime (`jobs::JobRuntime::run`, see *Background jobs* below), spawned once the API server is up and nothing fallible remains before supervision: a runtime spawned earlier and then orphaned by a bind error would leave claimed jobs locked until the reaper found them.
4. The events runtime (`events::EventsRuntime::run`, see *Events and the outbox*), spawned right after the job runtime, so SSE subscribers can exist before events flow.
5. The Discord gateway (`DiscordAdapter::run`, see *Chat channels*), when `DISCORD_TOKEN` is set: a second adapter in the same registry, spawned beside the Matrix loop.
6. The Telegram updates loop (`TelegramAdapter::run`, see *Chat channels*), when `TELEGRAM_BOT_TOKEN` is set: polling or webhook registration, spawned beside the other front doors.
7. The Email poller (`EmailAdapter::run`, see *Chat channels*), when `EMAIL_IMAP_URL` is set: IMAPS polling loop, spawned beside the other front doors.

The supervisor (`supervise_front_doors`) watches every adapter's task, not only Matrix's (B13): any front door or runtime that ends before shutdown was requested cancels the root token and stops the process, relying on the orchestrator to restart it. Each adapter's task is named per channel (`front_door_name`: "Matrix sync loop", "Discord gateway", "Telegram updates", "Email poller").

`BotHandles` (bot access token, Matrix SDK client, sync health, the live-client cell the job handlers read) is the coupling point: the REST layer borrows the *bot's* Matrix credentials to serve endpoints like `/rooms` and `/auth/media` that need homeserver access. A link begun in a chat is finished in the web UI through the database (`link_tokens`), not through shared memory.

**Shutdown is one `CancellationToken` tree, bounded at 15 s** (`app::SHUTDOWN_GRACE`, spec §5.3). `main.rs` owns the root and cancels it on SIGINT/SIGTERM (the handler is installed before boot, and boot's database connect is itself cancellable). The API server, every channel adapter, the job runtime and the events runtime each get a `child_token()`:

- The API server stops through axum's graceful shutdown. SSE responses never end on their own, so `sse_handler` ends its stream on the same token (`ApiState::shutdown`) — otherwise every open browser tab would hold the drain open until the deadline.
- The Matrix loop has every long await (client build, sync, backoff) inside a `select!` against `shutdown.cancelled()`. That structure is a deliberate fix: an earlier version awaited `bot.run()` inside a select *branch body*, where Ctrl-C could not reach it. Returning drops the running generation; no background work belongs to a sync generation any more (scheduled work is jobs, webhook delivery is the events runtime's dispatcher).
- The Discord adapter shuts its shards down, cancels its workers (an in-flight turn is dropped, as a Matrix turn is) and joins them before `run` returns.
- The Telegram adapter cancels its worker tasks, cancels setWebhook/getUpdates loops and joins them before `run` returns.
- The Email adapter cancels its polling loop, sets connected false and joins before `run` returns.
- The job runtime cancels its workers, gives in-flight handlers a 10 s grace, then hands the jobs they still hold back to the queue. It is stopped first, because releasing jobs needs the pool.

After cancellation `app::stop_by` waits for every task against one deadline (signal + 15 s); any task still running then is named in a `warn!` and aborted — not detached, so its drop guards run, and not awaited again, since a task stuck outside an await point would hold the process past the bound. `db.pool.close()` gets whatever remains of the same deadline. Finally `main.rs` drops the runtime with `shutdown_background()`, because an ordinary runtime drop waits without limit for in-flight blocking-pool work.

The `mcp` stdio mode is not part of the tree: it is a separate process invocation that ends at stdin EOF and starts neither front door.

`BotHandles` (`interface/channels/matrix/handles.rs`) also carries `sync_health: SyncHealth` — a lock-free `Arc<AtomicI64>` of the last completed sync's unix millis, written by the sync loop's `sync_with_callback` after every successful response and read by `/health/ready`. `sync_with_callback`, not plain `sync`, is the point of the change: it is the only hook that fires once per completed response rather than once for the whole (otherwise-infinite) sync loop, so it is the one place "a sync completed" can be observed and recorded.

## Events and the outbox

Every `SystemEvent` is stored before anything reads it. **The publish rule:** a service writes its state change and calls `repositories::outbox::publish(&mut tx, &event)` in the same transaction, then commits. `publish` takes a `Transaction`, so an event cannot exist without its state change, and a rollback leaves neither. Only `application/` publishes (`only_application_publishes_to_the_outbox` in `tests/architecture.rs`); the transaction scope is one state change, so a cross-service follow-up (reminder sync after a todo write, finance mirroring after a bill payment) commits its own events separately.

`publish` inserts one `outbox_events` row (`{type, payload}` as JSONB, keyed by `owner_id()`), plus one `outbox_deliveries` row per durable destination (`Destination`, always `<channel>:<id>`; today `WebhookTriggered` and `IdentityLinked` have one, e.g. `matrix:<room id>`). A trigger on `outbox_events` (0004) sends `NOTIFY outbox, '<event id>:<account uuid>'`, which PostgreSQL delivers at commit only.

```text
service tx ── outbox_events (+ outbox_deliveries) ── COMMIT ──► NOTIFY outbox
                                                                    │
                events::listener   (one LISTEN per process)  ◄──────┘
                    ├──► events::hub          ──► SSE subscriptions (this instance, per account)
                    └──► wake events::dispatcher ──► DeliverySink ──► Matrix room
events::purge (hourly) ── deletes events older than 30 days with no pending delivery
```

`events/` (`EventsRuntime`, built in `app::run`) is SQL-free and reaches the outbox only through `OutboxService`; `EventsConfig` holds every interval and bound. Its three tasks run under one child token, and a task ending before shutdown stops the runtime.

- **Hub and SSE.** The hub keeps this instance's subscriptions keyed by the account that authenticated them, so ownership is structural: a line is pushed only to its own account's subscribers. Each subscriber has a bounded channel (64); a full one is dropped, never awaited, and its browser's `EventSource` reconnects and refetches. The hub sends the stored JSON verbatim, and on a notification for an account with no subscriber it does not even load the event. Hubs are per instance: another process's browsers are served by that process's own listener.
- **Replay window.** Event ids commit out of order under concurrency, and a NOTIFY sent while the listener was down is gone. After every (re)connect, including a silent one sqlx performs inside `recv()` (hence the listener polls `try_recv` and treats `Ok(None)` as a reconnect), the listener replays `load_since(connected accounts, last_seen - 100, 500)` (the newest 500 rows) to the hub and wakes the dispatcher once. `last_seen` follows every notified id, subscriber or not, and is seeded from the outbox's max id on the process's first connect. Duplicates are harmless: the frontend treats each event as a cache invalidation.
- **Listener outage.** If `LISTEN` fails, SSE pauses and the listener retries every 30 s; nothing is lost from the database, and the reconnect replay closes the gap. The dispatcher does not depend on NOTIFY: it also polls every second.
- **Lease claiming.** The dispatcher claims due pending deliveries with `FOR UPDATE SKIP LOCKED` and, in the same statement, increments `attempts` and pushes `available_at` 60 s ahead. A crashed or timed-out claim therefore reappears on its own, and several processes never take the same row. Each send has a 30 s timeout (shorter than the lease) and is further capped by what is left of the lease minus a 5 s margin; every mark (delivered, retry, failed) is fenced by the `attempts` value the claim returned, so a claim that outlived its lease changes nothing, and claims left unsent (budget spent, shutdown) are released with their attempt restored. Retry time is computed on the database clock. A failure is recorded with `retry_delay` backoff up to `max_attempts` (10), then the delivery is `failed`.
- **Channel sink and idempotency.** `interface/events/channel_sink.rs` implements `events::DeliverySink` for `<channel>:<id>` deliveries (`Destination::Conversation`; `matrix:<room>` rows parse unchanged): it rebuilds the `WebhookAlert`, asks the destination adapter's `authorize_delivery` (Matrix: the webhook owner must be authorized for the room at delivery time) and sends through the `ChannelRegistry` with the idempotency key `outbox-<delivery id>`, which the Matrix adapter uses as the transaction id. A resend after a crash inside one Matrix session is therefore deduplicated by the homeserver; across a crypto-store reset it is at-least-once. The sink is ready while any adapter is connected.
- **No adapter connected.** While the sink is not ready (`ChannelRegistry::any_connected` is false) the dispatcher claims nothing, so an outage burns no attempts; deliveries wait as `pending` and are never purged. With one destination channel that is exact; with several, a delivery whose own channel is down is claimed, fails as not connected and backs off (R81, revisit when a second destination channel exists).
- **Never joins.** Outbox sends set `join_if_needed = false`: an alert may reach a room the bot is already in but must never make the bot join one, and the Matrix adapter's `authorize_delivery` refuses an unjoined room before sending. `IdentityLinked` (the link confirmation) is rendered by the sink from its `event_type` and skips `authorize_delivery` because its destination is the direct conversation the identity itself wrote to, not an owner-chosen room (R82).

## Background jobs

Reminders, morning briefings and portfolio alerts and refreshes run as durable jobs in PostgreSQL, not as polling loops owned by a Matrix sync session: a job survives a restart, its retries are bounded and visible in the `jobs` table, and a scheduler tick that runs twice enqueues once. The webhook delivery queue is unchanged until step 9 (outbox). Schema: [`database.md`](database.md#job-queue). Design: `superpowers/specs/2026-09-29-job-queue-design.md`.

| Job type | Enqueued by (cadence) | Dedupe key | Attempts / backoff | Handler (`interface/jobs/`) |
|---|---|---|---|---|
| `reminder.fire` | `ReminderService::enqueue_due` for each pending reminder with `trigger_at <= now` (5 s) | `<reminder_id>:<trigger_at>` | `MAX_DELIVERY_ATTEMPTS` (5) / 30 s | `reminders.rs` |
| `briefing.send` | `BriefingService::enqueue_due` for accounts whose local time is in the briefing window and whose `last_briefing_date` differs (30 s) | `<account>:<local date>` | 3 / 60 s | `briefing.rs` |
| `portfolio.check_alerts` | `PortfolioService::enqueue_alert_check`, only while an active alert exists and no earlier check is still open (120 s) | `alerts:<unix minute>` | 1 / none | `portfolio.rs` |
| `portfolio.refresh_prices` | `PortfolioService::enqueue_price_refresh`, one per holding owner (3600 s, first tick at start) | `<account>:<UTC hour>` | 3 / 60 s | `portfolio.rs` |

The flow is `scheduler tick (leader only) → application enqueue_due → jobs row (NOTIFY) → worker claim (SKIP LOCKED) → handler → service → Outbound → outcome`. Handlers parse a payload that carries row ids, call application services and deliver through the `Outbound` trait (`ChannelRegistry` in production), per the channel of the stored conversation; they hold no SQL and no business rule. The rules that decide what is due (`domain::reminders::next_occurrence`, the briefing window, the alert condition) are pure functions in `domain/`.

- **Runtime** (`backend/src/jobs/`). `JOB_WORKERS` workers (default 4, 1..=32) loop claim → run → record. Idle workers wait on `LISTEN jobs` or a 5 s poll, whichever comes first; a listener failure degrades to polling with a `warn!` and never stops the workers. A running job renews `heartbeat_at` every 30 s, and each handler run is bounded by its `timeout()` (default 5 min), which counts as a retryable failure. The reaper (every 60 s) requeues running jobs whose heartbeat is older than 2 min, counting the attempt; an hourly purge deletes finished jobs older than 7 days.
- **Leadership.** One scheduler task takes `pg_try_advisory_lock(SCHEDULER_LOCK_KEY)` on a connection detached from the pool (a session lock returned to the pool would stay held by the next borrower). The holder fires each tick at once and then at its cadence, pinging the lock connection before every round; if the connection dies it drops leadership and every instance retries every 30 s. The reaper and purge run on every instance, since both statements are safe to run concurrently.
- **Errors.** A handler returns `JobError::Retryable` (spends an attempt, backs off exponentially, `failed` after the last), `Permanent` (`failed` now; a malformed payload is always this) or `Unavailable(delay)` (a dependency is down: the job waits and the attempt is not spent). `AppError::Database` and `External` map to `Retryable`, the rest to `Permanent`. A job that reaches `failed` is logged at `error!`.
- **Matrix handoff.** The sync loop publishes each generation's client into a `MatrixHandle` (`interface/channels/matrix/live_client.rs`) and clears it when the generation ends; `MatrixAdapter` reads it. With no client every send is `NotConnected`, which handlers turn into `Unavailable(30 s)` (`CHANNEL_RETRY`), so an outage of a conversation's channel delays its deliveries without burning attempts. A stored room that is not an address, or `web`, is treated as delivered.
- **Shutdown.** The runtime runs under a child of the shutdown token. On cancel, workers stop claiming, in-flight handlers get `ctx.cancel` and a 10 s grace, and any job still running is released (back to `pending`, attempt refunded); this all sits inside the 15 s process bound.
- **Delivery is at least once.** A crash between the Matrix send and the commit repeats a message. The dedupe key stops a double tick from enqueuing twice, and every handler re-checks current state before acting: a reminder that was snoozed, cancelled or advanced is skipped, a briefing whose local date is no longer today is dropped, and the subject account is taken from the job row, never from the payload. A reminder whose job ended `failed` without the handler marking it is marked failed by the next `enqueue_due`, because the dedupe key would otherwise block a re-enqueue.

Adding a job type: add a `JobType` variant and a `NewJob` constructor in `domain/jobs.rs` (type, payload, attempts, backoff and dedupe key stay together); add the enqueue use case to the owning `application/<f>` service; write the handler in `interface/jobs/<f>.rs` and list it in `interface::jobs::handlers`; and, if it recurs, add a tick to `jobs/schedule.rs`. `jobs/` may not import axum, matrix-sdk, utoipa or `interface`, and neither it nor `interface/jobs/` may contain SQL (`tests/architecture.rs`).

## Chat channels

Matrix is one of several chat channels, and none of them owns a rule. The vocabulary is in `domain/channels` (pure, no I/O): `Channel` (`Matrix`, `Discord`, `Telegram`, `Email`), `PlatformUserId` (validated and canonical per channel), `PlatformIdentity`, `ConversationAddress`, `provisioning_policy` and the link decision `decide_link`. A conversation address has two spellings (R71): the **storage form** in the existing `room_id` columns (`web`, a bare Matrix room id such as `!abc:server`, or `discord:<id>`, `telegram:<id>`, `email:<addr>`), so rows written before other channels existed need no rewriting migration, and the **destination form** on outbox deliveries, always `<channel>:<id>` (`matrix:!abc:server`), so a sink routes on the prefix alone.

```text
platform event ─► adapter parses ─► Inbound pipeline ─► ModuleRegistry ─► <F>Service
                                        │  link before identity resolution
                                        │  IdentityService::resolve (provisioning policy)
reply ◄─ adapter renders ◄───────────── Reply { content, visibility }
jobs / outbox ─► ChannelRegistry::send(OutgoingMessage) ─► the target channel's adapter
```

- **`ChannelAdapter`** (`interface/channels/adapter.rs`) is the one trait object boundary: `channel`, `is_connected`, `run(cancel)`, `send(OutgoingMessage)`, and two defaulted hooks, `authorize_delivery` (outbox pre-check, `Result<(), String>` whose text is the delivery error) and `find_conversation_by_name`. There are four real implementations over time (Matrix and Discord now, then Telegram and Email), so the dynamic dispatch is a justified boundary; the neutral message types live in `message.rs` (`IncomingMessage`, `OutgoingMessage`, `Reply`, `Content`, `Attachment`, an opaque `MessageRef`, no metadata map, R72) and the pure HTML-subset renderers in `render/`.
- **`ChannelRegistry`** (`registry.rs`) holds at most one adapter per channel (`check_unique`), routes `send` by the target's channel (`NotConfigured` for an absent channel or `web`, `NotConnected` while the adapter is down) and `spawn_all` runs every adapter's `run` under a child token. Only `app.rs` builds adapters and the registry (`only_the_composition_root_builds_adapters_and_the_registry`); the pipeline holds a `Weak<ChannelRegistry>` because the registry owns the adapters that own the pipeline (A5).
- **Inbound pipeline** (`inbound.rs`) is everything between "the adapter parsed the text" and "the adapter sends the reply", written once. Order matters: **`link` is answered first, before identity resolution**, because resolving first would auto-provision an empty account for the very identity that is trying to link and turn every first link into a merge of nothing. Then `IdentityService::resolve` applies the channel's policy: Matrix auto-provisions an unknown sender (the bot stays usable without web signup); every other channel returns `Unlinked`, and an **unlinked identity gets only `start`, `help` and `link`** (every other command, and a direct free-text message, is answered with the "send /link" notice; free text in a shared conversation is ignored). A linked sender's text becomes a `ParsedCommand`, free text becomes the `ai` command where the bot is addressed, and dispatch runs inside a panic fence that answers with the fixed error reply. `interface/chat/link.rs` is the `link` handler the pipeline calls; it is deliberately not a `BotModule`.
- **`MatrixAdapter`** (`interface/channels/matrix/`) keeps everything Matrix-specific: the sync loop and reconnects, E2EE and verification, quote parsing (`quote.rs`), the dispatcher that decides which events are commands, attachments and voice upload, reactions, room membership and `rooms.rs`. It parses into `InboundText` and sends the reply with its own progress UI. Its `authorize_delivery` runs the old webhook sink's checks in their order and with their messages (connected, valid room id, bot already joined, owner authorized for the room), and `find_conversation_by_name` serves the AI outage alert.
- **`DiscordAdapter`** (`interface/channels/discord/`, registered only when `DISCORD_TOKEN` is set) speaks to Discord through `serenity`, which nothing outside that directory may name (`serenity_stays_inside_the_discord_adapter`). Gateway intents are `GUILDS | DIRECT_MESSAGES`, so no privileged intent is needed. Six slash commands (`/todo /expense /portfolio /ask /link /help`) each take one string (`args`, or `/ask`'s `prompt`) and reach the registry as the bare `todo add milk` modules already parse (B1); they are registered on every gateway ready, to `DISCORD_GUILD_ID` when set (instant) or globally. Text in a DM is free text for the agent (B3); guild messages are not received. The event handler only parses, refuses an invalid command ephemerally, **defers every interaction before anything else** (Discord allows three seconds) and queues the work on a bounded channel (32); four workers run the shared pipeline and edit the deferred response, with follow-ups for replies longer than one embed (B8). In a guild every command except `/help` is deferred ephemeral, and a `Private` reply is never posted on a public response (B2, spec invariant 10). Replies are embeds rendered by `render/markdown.rs` (no title, no colour), every message carries empty `allowed_mentions`, and `Content.actions` are not rendered (B5). Progress edits the deferred response at most every 1.5 s; DMs show the typing indicator. serenity reconnects a dropped session itself; when `Client::start` ends the adapter rebuilds the client with exponential backoff capped at five minutes, and an invalid token or disallowed intents end `run` with an error, which stops the process like any other front door (B7). `send` (jobs, the `IdentityLinked` confirmation) posts to a Discord channel or opens the user's DM, maps serenity errors to `ChannelError` (refused requests `Rejected`, 429 and 5xx `Transient`) and bounds every call by 30 s.
- **`TelegramAdapter`** (`interface/channels/telegram/`, registered only when `TELEGRAM_BOT_TOKEN` is set) speaks to Telegram through `teloxide-core` types and `Bot`, which nothing outside that directory may name (`teloxide_stays_inside_the_telegram_adapter`). Runs in one of two modes (`TELEGRAM_MODE=webhook` or `polling`). In webhook mode, `run` calls `setWebhook` at boot with exponential backoff (1 s doubling to 300 s) and updates arrive at `POST /api/webhooks/telegram`; in polling mode, `run` calls `deleteWebhook` and polls `getUpdates` with long-polling (timeout 50 s). Inbound updates are deduplicated by `RecentUpdates` (bounded at 1024 update IDs; T11). Updates arrive at a bounded queue (channel of 32); 4 worker tasks process updates concurrently. In webhook mode, incoming HTTP updates pass through `TelegramIngress`: rate-limited (120 req / 60 s per IP; T10), constant-time secret comparison against `X-Telegram-Bot-Api-Secret-Token` (T9), and enqueued (returning 200 immediately, or 503 if the queue is full) without logging the body or secret header. Commands (`/start /help /todo /expense /portfolio /link`) are advertised at boot via `setMyCommands` (T2), while any typed `/name` is parsed as a command. In direct chats, non-command text routes to the AI assistant; `/start` redispatches as `/help` for an unlinked user or when otherwise unhandled (T4). In groups and supergroups, privacy mode stays enabled: only slash commands (with optional `@bot` mentions), direct mentions, and replies to the bot's messages reach the bot; background group chat is not received (T3). `Private` replies in groups are refused with `PRIVATE_IN_GROUP` text ("That answer is private — message me directly.") and never posted to the public group (T8, spec invariant 10). Inline keyboards are constructed from `Content.actions` (`InlineKeyboardMarkup`, max 8 rows of 1 button, callback data ≤ 64 bytes; T6/T7). Callback queries are immediately answered (`answerCallbackQuery`) and executed under the presser's identity (not the message author's; T6, spec invariant 9). HTML formatting is rendered via `render/telegram_html.rs` (`TelegramHtmlRenderer`), mapping lists to bullet text and stripping unsupported tags while preserving valid Telegram HTML (T5). Agent progress is rendered via `TelegramProgress`: edits a status line message every 1.5 s, and DM interactions show the typing action indicator (T15). `send` (jobs, outbox deliveries) routes to direct or group chats, mapping teloxide errors to `ChannelError` (429/retry-after → `Transient`, 403 forbidden → `Rejected`).
- **`EmailAdapter`** (`interface/channels/email/`, registered only when `EMAIL_IMAP_URL` is set) handles email conversations via IMAP polling and SMTP delivery through `async-imap` and `lettre`, which nothing outside that directory may name (`email_crates_stay_inside_the_email_adapter`). Inbound emails are fetched periodically over IMAPS with `tokio-rustls`, deduplicated by `RecentMessages` (bounded at 1024 Message-IDs; E7), verified for DMARC pass against `EMAIL_AUTHSERV_ID` (E1, spec invariant 8: emails failing or lacking DMARC pass are dropped silently with no bounce/reply to prevent backscatter), and filtered against auto-replies / bounce loops (E2). Inbound bodies are parsed by `mail_parser`, stripped of trailing quotes and email signatures (E3), and submitted to the shared inbound pipeline. Commands run with `!` prefix or natural language routing to AI; agent progress uses `NoProgress` (E10). Outbound emails are sent via SMTP (`lettre::AsyncSmtpTransport`) as `multipart/alternative` (plain text fallback + clean HTML; E5, E6), with actions rendered as a bulleted text list (E6), in-reply-to threading preserved (E4), and timeouts bounded at 30 s (E14). Transient errors (4xx / network) return `ChannelError::Transient`, while permanent rejections (5xx) return `ChannelError::Rejected` (E14).
- **Outbound goes through the registry.** Job handlers take the narrow `Outbound` trait (`interface/jobs`; `ChannelRegistry` implements it, so handler tests keep a fake) and send to the channel of the stored conversation; a channel that is down is `Unavailable(30 s)` (see *Background jobs*). The outbox's `ChannelSink` (`interface/events/channel_sink.rs`, see *Events and the outbox*) delivers `Destination::Conversation` the same way. The AI outage alert targets the owner's `dev_room_id` (storage form) or the Matrix room named "dev", via the registry (A4).
- **`ProgressSink`** (`llm/progress.rs`) is how the agent reports stages, tool calls and streamed text without knowing a channel; each adapter supplies its own (Matrix edits one message in place) and `NoProgress` is the null sink. `llm/` and `application/` import no channel SDK or `interface::channels` (`the_agent_knows_no_channel`, `application_knows_no_channel_sdk`); `domain/channels` stays pure (`channel_domain_is_pure`); adapters run no SQL (`channel_adapters_run_no_sql`); `interface/chat` modules know no platform SDK (`chat_modules_know_no_platform_sdk`).

### Multi-channel operational behavior & invariants

1. **Format Normalization (`render/`):**
   - Application modules author messages using a clean, semantic HTML subset (`<b>`, `<code>`, `<blockquote>`, `<a>`, `<pre>`, `<ul>`/`<li>`).
   - Adapters normalize this representation for their medium:
     - **Matrix:** Native HTML with `html_escape()`, clean plain-text fallback via `strip_html()`, and MSC3245 audio bubbles for speech.
     - **Discord:** Converted to Markdown via `render/markdown.rs` (rich embeds, tabular codeblocks, empty `allowed_mentions` to prevent mention spam).
     - **Telegram:** Converted to Telegram HTML via `render/telegram_html.rs` (strips unsupported tags, preserves formatting, splits messages > 4096 characters).
     - **Email:** Rendered as `multipart/alternative` via `render/email.rs` (plain text + sanitized HTML, action buttons converted to numbered lists).
2. **Channel Privacy Models & Visibility Gating:**
   - **Direct Messages:** Full personal workspace access across all channels (`!finance`, `!portfolio`, `/ask`, etc.).
   - **Public / Shared Channels:**
     - Matrix: Sensitive commands reply with `Visibility::Private` or are refused outside DM.
     - Discord: Every guild command (except `/help`) is deferred **ephemeral** (visible only to the invoking user). `Visibility::Private` is strictly forbidden from posting publicly.
     - Telegram: Group privacy mode is strictly enforced. `Visibility::Private` replies are refused with `PRIVATE_IN_GROUP` notice ("That answer is private — message me directly.").
     - `/link` is strictly refused in any public channel/room on all platforms.
3. **Outbox Delivery Fencing & Offline Deferral (R166):**
   - Deliveries are fanned out per destination through `outbox_deliveries`.
   - Before claiming a delivery, the outbox dispatcher verifies that the specific destination channel adapter is connected. If an adapter is offline (e.g. Discord gateway reconnecting or Matrix homeserver maintenance), pending deliveries for that channel are deferred *without burning retry attempts*. They resume immediately upon adapter reconnection.
4. **Rate Limiting & Inbound Flow Control:**
   - **Discord:** Workers throttle message editing to at most once per 1.5s to avoid 429s, deferring interactions immediately within 3s.
   - **Telegram:** Inbound webhook requests are rate-limited to 120 req / 60s per IP, verified using constant-time secret comparison against `X-Telegram-Bot-Api-Secret-Token`. Outbound requests deduplicate identical rapid messages within a 60s window (`TelegramSendDeduper`, R168).
   - **Email:** Inbound emails are deduplicated via a 1024-entry `Message-ID` sliding window. Emails without a valid DMARC pass matching `EMAIL_AUTHSERV_ID` are dropped silently with zero bounce or reply, preventing email backscatter.

### Identity and linking

`platform_identities` maps `(platform, platform_user_id)` to one account; an account may hold many, across channels. `application/identity` (`IdentityService`, `LinkService`) is the only writer. Linking proves two things separately: the **direct conversation** that asked proves ownership of the chat identity, the **passkey session** that claims proves ownership of the account.

1. `link` in a direct conversation (`!link`, `/link`): `LinkService::start` refuses a shared conversation before minting anything, burns the identity's previous live token, stores the SHA-256 of 32 random bytes with the asking conversation and a 10-minute expiry, and the reply carries `<WEB_URL>/link?token=…` (shown once, in that conversation and the URL).
2. The landing page (`/link`, `frontend/src/modules/link/LinkPage.tsx`) calls `POST /link/inspect` for a preview chosen by `decide_link` and the viewer: `bind`, `already_yours`, `needs_merge` (with what moves), `owned_elsewhere`, `signup_allowed`, `sign_in_required` or `expired`. It reads only.
3. `POST /link/claim` needs a fresh passkey assertion. In one row-locked transaction it binds the identity (merging first when the holder is an unclaimed auto-provisioned account, or when the identity was last unlinked from an account that still holds data, A3), records the audit row, burns the token and publishes `IdentityLinked`, whose delivery tells the asking conversation "account linked". A claimed account's identity is never taken (`owned_elsewhere`). Any failure leaves the token usable and nothing changed.
4. An identity on the deployment's signup allowlist (`DISCORD_ALLOWED_USERS`, `TELEGRAM_ALLOWED_USERS`, `EMAIL_ALLOWED_SENDERS`) may instead create an account with a passkey from the same token: the finish step creates the account, stores the passkey and binds the identity in one transaction and rolls all of it back if the bind is refused.

Unlinking (`IdentityService::unlink`, web only, step-up) removes one identity and records `identity_unlinked`; it refuses to remove the last way in of an account with no passkey, under a lock on the account row. Data stays with the account.

## Chat command plugin system

`BotModule` (`interface/chat/mod.rs`) is the extension point for chat commands, shared by every channel: one `ModuleRegistry` serves all adapters. `ModuleRegistry::dispatch` walks modules in registration order and returns the first `Some(Reply)`; registration happens in `interface/channels/matrix/modules.rs::build_modules` and **order matters** (the TTS module must be registered before the AI module's direct-message catch-all, and a test pins that). `CoreModule` receives an `Arc<RwLock<Option<Arc<ModuleRegistry>>>>` back-reference so `!help` can enumerate all modules — a deliberate cycle-breaking indirection; keep it if you touch help generation. Modules answer through `Reply` (`Reply::private` for finance, portfolio, journal, life, settings and account replies, which only matters to channels with public conversations, R78) and know no platform SDK.

A module only handles commands; scheduled work (reminders, briefings, portfolio) is jobs, see *Background jobs*, and event delivery is the outbox, see *Events and the outbox*. `interface/channels/matrix/dispatcher.rs` accepts a message either when it starts with `!` or when the bot is mentioned, strips the HTML mention pill, and yields the Matrix parse the pipeline consumes.

Room caching and target-room resolution belong to `application/rooms` (rules in `domain/rooms`, Matrix-side discovery in `interface/channels/matrix/rooms.rs`). `interface/http/rooms.rs::list_rooms` is a *room picker* feed, not a room dump: it drops spaces, DMs, rooms not in `RoomState::Joined`, rooms lacking a name or canonical alias, and any room where the bot is not joined or *none* of the caller's linked MXIDs is. An account can have several Matrix identities, so "the caller" is a set; an account with no link gets an empty list, which is the honest answer rather than an error.

## Matrix session and crypto store

`interface/channels/matrix/client.rs` treats `data/matrix_session.json` and `data/bot_store/` as **one unit**: the session is reused only when `restore_session` plus a live `whoami` both succeed, and any other path (no session file, rejected token, device deleted in a client) archives the store to `data/bot_store.orphaned-<UTC timestamp>/` before logging in fresh. Never keep the crypto store across a fresh login — its Olm account belongs to the dead device, the crypto machine believes it already published those keys, and every message the bot then encrypts shows in Element as "Encrypted by an unknown or deleted device". The store is archived rather than deleted because it may hold the only copy of room keys that never reached key backup; `MATRIX_RECOVERY_KEY` is what repopulates a fresh store (`restore_room_keys_from_backup`).

A fresh login does **not** pin a device ID. It used to (`MATRIX_BOT_MAIN_DEVICE`, constant across every restart), which silently rotated that device's keys under the same ID on every restore failure — routine, not rare, since "no session file / rejected token / device deleted in a client" are the normal triggers. The homeserver accepts that re-upload without complaint, but every peer who already talked to the old device keeps encrypting *to* it using its old keys: the peer is the sender in that direction, so it never hits a decrypt error and has no trigger to rebuild its Olm session. The result is exactly the failure mode the paragraph above guards against — except it was also happening on ordinary token-rejection restarts, not just on manual device deletion. Now `client.rs::delete_stale_device` captures the outgoing device's ID before a fresh login (session file must be read *before* `restore_previous_session` deletes it on failure), logs in with **no** pinned ID so the homeserver assigns a fresh one, then deletes the old device via password-authenticated UIA once the new session is live. Every fresh login now presents as an unambiguous new device to every peer — the well-tested "new device, verify me" path — instead of an in-place key swap peers have no reliable way to notice.

## Verification (self and peer)

`interface/channels/matrix/self_verify.rs::ensure_self_verified` makes the bot's own session show as *Verified* in Element without a human: it signs the bot's device with the account's own self-signing key (imported from `MATRIX_RECOVERY_KEY` via secret storage) and retries because the SDK's own attempt inside `Recovery::recover()` races the first sync — it silently finds nothing to sign if the device isn't in the crypto store yet, and `recover()` returns `Ok` either way, so treat that `Ok` as "secrets imported," never as "verified." `interface/channels/matrix/verification.rs::request_verification_from_allowlist` handles the *other* trust edge — an allowlisted human verifying the bot — by sending the request from the bot's side on every boot (a client that refuses unverified sessions would otherwise block the very `!verify` message that starts the flow) unless `data/verified_users.json` already records a completed SAS with that user; that file is the only signal treated as durable, because `UserIdentity::is_verified()` reports only *our* signature over *them* and was observed true while their client was still refusing to send to the bot.

`interface/channels/matrix/self_verify.rs` is what keeps the session from showing as *Unverified* in Element. Element's rule is cross-signing: the account's self-signing key must have signed the device, with the signature on the homeserver. A password login mints unsigned device keys, so signing has to follow it — that second step, not the password, is why an Element login looks verified and a bare bot login does not. `MATRIX_RECOVERY_KEY` unlocks secret storage for two independent things: the cross-signing keys (which make the session verified) and the megolm backup key (which makes history decryptable). An account whose secret storage carries only the latter recovers its room keys and stays unverified forever.

`ensure_self_verified` runs on **every** boot, after `recover()` but regardless of whether a recovery key was configured or worked — a restored crypto store already holds the self-signing key, so a restart re-verifies with no recovery key involved. Do not fold it back into the `recover()` success branch. It retries because a fresh login races itself: the SDK attempts the same signing inside `Recovery::recover`, but only when our device is already in the crypto store, and our device keys are still uploading on the first sync — so that attempt silently finds nothing to sign while `recover()` still returns `Ok`. **Never treat `recover()` returning `Ok` as a verified session.**

Two measured facts about matrix-sdk 0.7 drive the shape of that code. `Recovery::recover` returns `Ok` even when secret storage held no self-signing key and nothing was signed (`SecretStore::import_secrets` gates signing on `has_self_signing`, and a missing secret reads as `None`, not an error). And `Device::is_cross_signed_by_owner()` on our *own* device keeps reporting false for at least a second after the signature is uploaded and re-queried, across restarts, even though `/keys/query` shows it — so the outcome is taken from `Device::verify()` returning `Ok` (the signature reached the server), never from a local re-read. Consequently the bot re-signs on most boots; that is intended and idempotent.

*(Re-measure on 0.18 at first boot — see `superpowers/runbooks/postgres-foundation-cutover.md` step 4. These facts predate the matrix-sdk 0.18 upgrade and have not yet been reconfirmed against it.)*

The acceptance test is `self_verify.rs::test_the_running_bot_session_is_verified_on_the_homeserver` — `#[ignore]`d because it needs credentials, a network, and a bot that has run at least once. It reads the token the running bot saved and asks `/keys/query`, applying Element's own rule via `device_is_cross_signed`; it never logs in, because a second login would mint another device and leave the running session's token to be reasoned about separately.

## Accounts: one owner, several ways in

`accounts` is the only thing that owns a row. `owner_id` — the column on every data table — holds an `accounts.id` and nothing else. The id is a native PostgreSQL `UUID`, typed `AccountId` in Rust and rendered `acct_<32 hex>` on the wire and in the portfolio audit hash (see [`database.md`](database.md#account-ids)).

Two access paths resolve onto it and are then indistinguishable:

- A chat message resolves through `platform_identities` (the inbound pipeline → `IdentityService::resolve`, which applies the channel's provisioning policy; see *Chat channels*).
- A web session resolves directly from the session cookie: `interface/http/auth/credential.rs::parse_credential` reads the headers, `AccountService::resolve_credential` looks the credential up and returns a `Principal`.

The pieces live in `domain/accounts` (`AccountId`, `Credential`, `Principal`, the session and security constants, `OWNED_TABLES`), `application/accounts` (`AccountService`: principal resolution, recovery, passkeys, sessions, security events; `MergeService`), `application/identity` (`IdentityService`, `LinkService`) and `infrastructure/postgres/repositories/accounts/`. `AccountService` is the only writer of `security_events`: `tests/architecture.rs::interface_never_writes_security_events` keeps the write calls out of `interface/` and `llm/` (and event kinds out of everything but the Matrix DM wording), so an audit row cannot be written twice by a handler and a service.

This replaced two disjoint identity spaces: `owner_id` used to hold a raw MXID for anything created over Matrix and `@web-<username>:api` for anything created through the API, so **one human using both saw two separate datasets**. Ownership is now carried, never derived. `AuthUser::owner_id()` returns `account_id` verbatim; if you ever find yourself computing an owner from a subject, that is the bug this design exists to remove.

An unknown MXID gets an **unclaimed** account: real data, no credential, reachable only through that MXID. That is what keeps the bot usable with no web signup. `UNIQUE (platform, platform_user_id)` on `platform_identities` alone enforces "one chat identity, one local account" — schema-level, so a concurrent link cannot race it. `identities::resolve_or_provision` creates the account and binds in one transaction and rolls back on a lost race, so no orphan is left to delete (R74).

The merge (`application/accounts/merge.rs`, with its allow-listed dynamic SQL in `infrastructure/postgres/merge.rs`) absorbs one account into another, rewriting every table `OWNED_TABLES` (`domain/accounts`) lists: a table missing from it is a silent data leak, not a compile error. Sessions do **not** follow a merge — a session belongs to the credential that opened it.

## Per-user settings (timezone, default currency)

Settings is a layered feature (`domain::settings`, `application::settings::SettingsService`, `infrastructure/postgres/repositories/settings.rs`, `interface/chat/settings.rs`'s `SettingsModule`) whose data every *other* feature reads — todo and reminder format timestamps against the sender's zone, finance and portfolio default an amount's currency to it — and which `interface/http/settings.rs` exposes to the web UI. Rows in `user_settings` are keyed by `owner_id`, the same account key every other table uses, and a user has no row until they change something: this is a domain rule (`UserSettings::default()`, UTC/USD), not something baked into SQL — the repository returns `None` for a missing row, and `SettingsService::get`/`get_or_default` apply the default. `get_or_default` additionally swallows a database error into the defaults for a read that must not fail the caller's own work (a command reply, another feature's read path) — a settings lookup must never be the reason a `!todo list` reply is lost.


Every write goes through `SettingsService`, which validates `timezone`/`currency` before persisting regardless of what built the row (`save`), or reads-modifies-writes one field at a time in a single transaction with the row locked (`modify`, `SELECT ... FOR UPDATE`) so two concurrent changes for the same owner cannot interleave and lose one side's update. `SettingsService` publishes `SettingsUpdated` (through the outbox, in the save's transaction) on a successful save and on nothing else — a read or a rejected value announces no change. Portfolio follows the same discipline (below).


`utils::format_datetime` takes a `chrono_tz::Tz` rather than assuming UTC, and `todo`/`reminder` handlers resolve the sender's zone once, *after* the command is claimed, so an unrelated room message costs no query. The finance handler's `DEFAULT_CURRENCY` constant is gone: `parse_entry` takes the sender's saved currency, so `!expense add 9.99 coffee` books in what they actually spend. An explicit code in the command still wins.

Validation is a domain rule (`domain::settings::parse_timezone`/`parse_currency`/…), applied at every boundary that writes — the HTTP `PUT` handler, each Matrix `!settings` subcommand, and the AI tool alike — not at render time: an unknown zone stored now would render as UTC on every later read with nothing to point at. `parse_timezone` accepts exactly the IANA names `Intl.supportedValuesOf('timeZone')` offers the picker; `parse_currency` requires a 3-letter code, and `domain::finance::money::normalise_currency` delegates to it rather than re-deriving the same rule.

On the frontend, `core/settings.ts` is the single source — `useSettings()` reads one shared React Query entry, so a change reformats the whole app from one cache write. Anything rendering an instant must pass the zone explicitly (`formatDateTimeInZone` and friends); a bare `toLocaleString` silently uses the browser's zone, which is exactly what the setting exists to override. The same applies in reverse for *input*: `zonedInputToUtcIso`/`utcIsoToZonedInput` convert the `DateTimePicker`'s naive `YYYY-MM-DDTHH:mm` against the chosen zone, applying the offset twice so a daylight-saving boundary cannot land the result an hour out. `DateTimePicker` itself stays zone-agnostic and takes a `now` prop purely so "today" and the "Now" button mean the right day.

## Voice replies (`!say`)

`interface/chat/tts` speaks a reply into the room as a native Matrix voice message. It prepares the text (`text.rs` strips HTML and emoji — the phonemiser has no reading for `🔊` or `✅`, and leaving them in produces unpredictable silent gaps mid-sentence), resolves which voice speaks, and uploads the result. Synthesis itself happens elsewhere: `infrastructure/inference/tts` reaches `POST /v1/audio/speech`, served by the bundled inference server's Kokoro (`inference/src/tts/kokoro.rs`) or by any OpenAI-compatible or ElevenLabs provider, chosen by `TTS_BASE_URL` / `TTS_DIALECT`. An unset base URL makes `!say` answer that speech is unavailable, and nothing else changes — the same degrade-one-feature shape `infrastructure/inference/ocr` and `infrastructure/inference/stt` use.

The reply is **Ogg Opus, not WAV**, and that is what makes a client draw a voice bubble instead of a file card. The bundled server adds `X-Duration-Ms` and `X-Waveform` response headers, which a Matrix voice message needs and raw audio does not carry. A provider that omits them — every third-party one — still produces a bubble: `infrastructure::inference::tts::ogg_opus_duration` reads the duration straight from the Ogg container, the last page's granule position minus the `OpusHead` pre-skip, and the bubble simply has no amplitude bars. The granule arithmetic of the encoder itself (`inference/src/tts/opus.rs`) has no equivalent local check; it is verified externally with `ffprobe` over the route's own output.

The per-user voice is `user_settings.tts_voice: Option<String>`, and `TTS_VOICE` is the house default for someone who has never chosen. It is an `Option` rather than a plain string for the same reason it was an `Option<i64>` before this crate split: `"0"` is a real Kokoro voice, so a bare default would make "never customised" and "chose voice 0" indistinguishable. `!settings voice <voice|none>` validates only the *shape* of a saved value (`parse_tts_voice`) — a Kokoro id, an OpenAI name and an ElevenLabs id all fit the same shape, and the bot has no way to know which voices a configured provider actually has. The bundled server is the one place that does know: it clamps an out-of-range Kokoro id to the nearest valid voice (`kokoro::clamp_speaker_id`) rather than failing the request, and answers 400 to a voice that is not an integer at all.

The Kokoro engine loads once into a `static OnceLock`, deliberately unlike `inference/src/stt/sherpa.rs`, which rebuilds its SenseVoice recogniser on every call — that is fine for a small model loading in milliseconds and wrong for Kokoro, which is 311 MB and takes seconds. It is provisioned at inference server startup the same way the other models are: downloaded from the sherpa-onnx `tts-models` release archive, unpacked into a staging directory, and renamed into place so a route never sees a partial model. Its text-normalisation FSTs ship inside that same archive.

Two build facts follow from the encoder and the runtime living in a separate crate. `matrix-bot-inference` needs `cmake`, because `opusic-sys` compiles a vendored libopus from source for `inference/src/tts/opus.rs`; the bot needs neither `cmake` nor any sherpa shared library at all. On a Windows development machine, a test that loads the real Kokoro model needs sherpa's own `onnxruntime.dll` copied into `target/debug/deps/` — see that test's own comment in `inference/src/tts/kokoro.rs` for why a version mismatch there dies with an access violation rather than a clean error.

## External services and the inference crate

The workspace has two members. `backend/` builds `matrix-bot`; `inference/` builds `matrix-bot-inference`, an Axum server that hosts the local ONNX models. `default-members = ["backend"]` keeps bare `cargo run` meaning the bot, and `cargo test -p matrix-bot` is the everyday suite — `cargo test --workspace` additionally builds the crate carrying the native ML dependencies, which is why CI scopes the backend jobs explicitly.

OCR reaches the inference server over HTTP via `infrastructure/inference/ocr`, speech to text via `infrastructure/inference/stt`, and text to speech via `infrastructure/inference/tts`. STT speaks OpenAI's `POST /v1/audio/transcriptions` — so `STT_BASE_URL` can point at the bundled server, OpenAI, Groq or anything else with that shape, and `STT_API_KEY` is sent as a bearer token. The client asks for `response_format=json`, the one format every compatible transcription model accepts (OpenAI's `gpt-4o-*-transcribe` models reject `verbose_json`); a voice note's duration prefers the provider's own figure when one comes back, falling back to the Matrix event's own `AudioInfo.duration` otherwise — a `json` response carries none, so that fallback is the usual case. Text to speech reaches `POST /v1/audio/speech` via `infrastructure/inference/tts`, which speaks the OpenAI shape and, under `TTS_DIALECT=elevenlabs`, the ElevenLabs one. An unset base URL, or an unreachable server, degrades that one feature: the bot still boots and stays a working bot without it, given a reachable PostgreSQL `DATABASE_URL` — there is no local-volume fallback for the application database.

The inference server provisions models in the background (`provision.rs`), spawned beside the listener rather than awaited in front of it, so `/health` answers at once and each route reports 503 until its own files land. Every wire contract between the two crates that a client actually consumes is a JSON fixture in `contracts/` asserted by both sides — a format only one side speaks (the inference server's `verbose_json`, which the bot never requests) is asserted by that side alone — because the two crates' types are separate by design and nothing else would notice a renamed field.

`backend/src/infrastructure/inference/` is the boundary this split created. `interface/` and `application/` define what the application does; `infrastructure/` is how external capabilities are reached. Nothing in `infrastructure/` may import from `interface/` or `application/` — `infrastructure::inference::ocr::OcrScan` is a separate type from `interface::chat::ocr::OcrResult` for exactly that reason, with a `From` impl doing the mapping.

## Object storage and media decoupling

Binary media (receipt photos, voice audio clips, attachments, data exports) is decoupled from PostgreSQL: state, transactions, and metadata remain in PostgreSQL, while binary payloads live in pluggable object storage accessed via `StorageService` (`infrastructure/storage/mod.rs`).

- **Domain keys (`domain/storage/mod.rs`):** `StorageKey` is a strict, synchronous domain value object enforcing the format `accounts/{account_id}/{category}/{uuid}.{ext}`. Path traversal sequences (`..`, `\`, leading/trailing `/`, non-whitelisted characters) are rejected at instantiation before reaching any filesystem or cloud driver. `StorageCategory` enforces domain partitions (`Receipts`, `Audio`, `Attachments`, `Exports`).
- **Pluggable drivers (`infrastructure/storage/`):**
  - `LocalStorageService`: Writes atomically via staging `.tmp` files into `STORAGE_LOCAL_DIR` (default: `data/storage`) and generates HMAC-SHA256 presigned URLs.
  - `S3StorageService`: Works with AWS S3, Cloudflare R2, MinIO, or compatible providers using `aws-sdk-s3`. Presigned URLs are minted natively via AWS S3 presigning.
- **Isolation:** `backend/tests/architecture.rs::storage_crates_stay_inside_the_storage_infrastructure` enforces that `aws-sdk-s3` and `aws-config` are strictly private to `infrastructure/storage/` and never leak into `application/`, `interface/`, or `domain/`.
- **Media Ingestion & Async Processing:** Inbound chat attachments (such as receipt photos) are saved directly to `StorageService` with `StorageCategory::Receipts`. An acknowledgment is immediately returned to the chat channel, while a durable background job `media.process_receipt` (`interface/jobs/media.rs`) is enqueued. The worker executes OCR, parses receipt fields, records the transaction with `receipt_storage_key` via `FinanceService::record_expense`, and notifies the originating conversation via outbox.
- **Streaming endpoint:** `GET /api/v1/storage/*key` validates either active caller session matching the account prefix in the key or an unexpired HMAC signature, streaming binary media with proper `Content-Type`.

## Portfolio (investment holdings)

Portfolio tracks investment positions — symbol, quantity, weighted-average cost basis. A holding's price is set manually (`!portfolio price`, the web UI) or refreshed from the quote feed in `infrastructure/web/portfolio_feed.rs` (`!portfolio refresh`, `POST /portfolio/refresh-prices`); market value and unrealized P&L are `Option`, not zero, until a price exists.

Quantity goes through the same integer-minor-units technique `finance::money` uses for currency, at a fixed `QUANTITY_EXPONENT = 8` (enough for a fractional share or satoshi-level crypto) — `parse_amount`/`format_amount` are currency-agnostic, so `portfolio` calls them directly rather than reimplementing decimal parsing. Weighted-average cost on a buy, and realized P&L on a sell, both rely on quantity's `10^8` scale cancelling against the divisor in `domain/portfolio/models.rs` (`weighted_avg_cost_minor`, `realized_pl_minor`) — the arithmetic is `i128` throughout because a large crypto quantity times a large price can approach `i64`'s ceiling. A second currency for a symbol already held is rejected (`BuyOutcome::CurrencyMismatch`), the same principle as `finance` never summing two currencies: there is no rate source to reconcile them.

Selling the full quantity held deletes the row — average cost has no meaning for a position of zero. `portfolio_holdings` has no `room_id`/`sender_name`, unlike `transactions`: a holding is a per-owner aggregate like `finance_categories`, not a room-broadcast event log, so there is nothing room-scoped to record.

**Cash is a hard precondition for buying, never for selling.** `portfolio_cash_balances` holds one row per `(owner_id, currency)`, the same "no row until you touch it" convention as `user_settings` — a missing row reads as a zero balance, enforced in the repository, not a schema `CHECK`. `PortfolioService::buy` delegates to `infrastructure/postgres/repositories/portfolio/trades.rs::buy_at`, which is the funding gate: the "is there enough?" check, the debit and the holding write happen in one transaction, so there is no separate check-then-act window for a concurrent buy to race — if funds are short, `BuyOutcome::InsufficientCash` comes back and *nothing* is written, on either table. `sell` always succeeds in crediting cash with the **gross proceeds** (`cost_of(qty_sold, sell_price)`), not the realized P&L — a losing sale still returns the principal that came back out. `set_price`/`set_note`/`delete` never touch cash: only `buy` and `sell`, the two commands that represent an actual money-for-shares exchange, do. Because the holding write and the cash write share that transaction, a buy cannot debit cash without recording the position.

## Frontend module mirror

The SPA mirrors the backend plugin shape: `core/registry.ts` holds `FrontendModule`s registered in `App.tsx`, one per feature (dashboard, todo, reminder, finance, portfolio, AI and the rest). Each module supplies a `MainView`, optional `navTab`/`getStatItems`, and a `handleSseEvent(event, queryClient)` used to invalidate React Query caches from the live stream (`core/useSystemEvents.ts`). Adding a backend module means adding a matching `frontend/src/modules/<name>/index.tsx` and registering it in `App.tsx`.

All API calls go through `core/apiClient.ts` (`fetchApi`), which sends `credentials: 'include'` — the session is an HttpOnly cookie, so there is no token to read or store — and unwraps the standardized `{ "error": "...", "code": 400 }` shape produced by `backend/src/error.rs::ApiError`.

`core/session.ts` is the single source of "who is signed in": the cookie is unreadable by the page, so only the server can answer, and `useSession()` asking `/auth/me` is that answer. There is deliberately no client-side token to inspect and nothing that can drift from the server's view.

`core/security.ts::useSensitiveAction` wraps any step-up-gated call. A 403 is not an error to show someone — it is the server asking for a passkey — so it prompts, retries, and only reports a second failure.
